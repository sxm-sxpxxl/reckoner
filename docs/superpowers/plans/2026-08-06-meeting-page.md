# Meeting Page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Страница встречи целиком: сводка, участники, история операций, блок «Кто кому должен» в трёх представлениях, лог изменений и все модалки — участник, расход с долями, перевод, правка встречи.

**Architecture:** Всё, что показывает страница, приходит одним запросом `GET /api/meetings/:id` уже посчитанным. Любая мутация возвращает встречу целиком, и её ответ кладётся в кэш — второго запроса нет, рассинхронизации нет. Единственная арифметика на клиенте — живое превью долей в модалке расхода, и оно намеренно повторяет серверный алгоритм, а не заменяет его.

**Tech Stack:** React 19, TypeScript 6, TanStack Query 5, CSS Modules, Vitest.

## Решения, принятые до начала

**Превью долей считает то же, что сервер, и это дублирование осознанное.** В модалке расхода
сумма против каждого имени обновляется на каждый ввод — сходить за ней на сервер нельзя, записи
ещё нет. Поэтому `sharePreview.ts` повторяет алгоритм из `domain/shares.rs`: целочисленное
деление, остаток по наибольшей дробной части, тай-брейк по `position`. Единственный источник
истины — по-прежнему сервер: превью показывает, а сохраняет и пересчитывает он. Расхождение
поймает Task 6 — тесты берут те же числа, что доменные тесты в Rust.

**Кнопка «Отдано» — обычный перевод.** Отдельной ручки нет и не будет: это `POST /entries`
с `kind: "transfer"`. Так же решено на сервере, где текст лога у обоих один.

**Время в истории и логе — `24.07, 23:00`, с запятой.** Текст хендоффа говорит `дд.мм чч:мм`
без неё, но на скриншотах 03 и 04 запятая есть в обоих местах, а скриншоты объявлены
high-fidelity. Правим `formatLogTime` и его тест.

**Бейдж на странице встречи не такой, как на карточке.** На карточке «Осталось 3», на странице
«Осталось переводов: 3» — так на скриншотах 01 и 02. Значит подпись зависит от места, и
`STATUS_TONES.label` для этого не годится: добавляем второй набор подписей, а цвета остаются
общими.

**Обложка в этом плане только показывается.** Дропзона рисуется с пустым состоянием из хендоффа,
но загрузка файла — план 6 вместе с серверными ручками, сжатием на клиенте и `ETag`. Пока зона
не принимает `drop`: показывать активную зону, которая молча ничего не делает, хуже, чем
честно неактивную.

**Раскрытые должники по умолчанию раскрыты** — как в прототипе (`expanded` по умолчанию `true`).

**Диалог подтверждения удаления — свой, не `confirm()`.** Нативный `confirm` в модалке на iOS
блокирует страницу и выглядит чужеродно.

### Task 1: Запросы и мутации встречи

**Files:**
- Modify: `frontend/src/api/meetings.ts`

- [ ] **Step 1: Дописать хуки**

Все мутации получают ответом встречу целиком, поэтому у всех один `onSuccess`: положить
её в кэш по `meetingKeys.one(id)` и инвалидировать список (там меняются сумма, статус
и состав участников).

Нужны: `useMeeting(id)`, `useUpdateMeeting(id)`, `useDeleteMeeting()`,
`useAddParticipant(id)`, `useUpdateParticipant(id)`, `useRemoveParticipant(id)`,
`useAddEntry(id)`, `useUpdateEntry(id)`, `useRemoveEntry(id)`.

Общий помощник, чтобы не повторять `onSuccess` девять раз:

```ts
/** Ответ мутации — уже посчитанная встреча, поэтому кладём её в кэш вместо
 *  повторного запроса. Список инвалидируем: в нём меняются сумма и статус. */
function useMeetingMutation<TBody>(
  meetingId: string,
  send: (body: TBody) => Promise<Meeting>,
) {
  const queryClient = useQueryClient()

  return useMutation({
    mutationFn: send,
    onSuccess: (meeting) => {
      queryClient.setQueryData(meetingKeys.one(meetingId), meeting)
      queryClient.invalidateQueries({ queryKey: ['meetings'] })
    },
  })
}
```

### Task 6: Превью долей

**Files:**
- Create: `frontend/src/domain/sharePreview.ts`, `frontend/src/domain/sharePreview.test.ts`

- [ ] **Step 1: Написать падающие тесты**

Числа берутся из доменных тестов Rust — так расхождение превью с сервером станет
видно сразу:

```ts
import { describe, expect, it } from 'vitest'
import { previewShares } from './sharePreview'

/** Участники в порядке `position`, как их отдаёт сервер. */
const four = ['a', 'b', 'c', 'd']

describe('previewShares', () => {
  it('делит поровну, когда доли не заданы', () => {
    expect(previewShares(400, four, {})).toEqual({ a: 100, b: 100, c: 100, d: 100 })
  })

  it('раздаёт остаток по наибольшей дробной части, тай-брейк по порядку', () => {
    // 100 на трёх → 34 / 33 / 33: лишний рубль уходит первому по позиции.
    expect(previewShares(100, ['a', 'b', 'c'], {})).toEqual({ a: 34, b: 33, c: 33 })
  })

  it('учитывает четверти', () => {
    // Веса 1, ½, ½ на 100 ₽ → 50 / 25 / 25.
    expect(previewShares(100, ['a', 'b', 'c'], { b: 2, c: 2 })).toEqual({ a: 50, b: 25, c: 25 })
  })

  it('нулевая доля не платит ничего', () => {
    // Веса 1, ½, 0, 1 на 100 ₽ → 40 / 20 / 0 / 40.
    expect(previewShares(100, four, { b: 2, c: 0 })).toEqual({ a: 40, b: 20, c: 0, d: 40 })
  })

  it('если у всех доля 0 — считаем всех по одной', () => {
    // Так же поступает сервер: иначе расход не разделить вообще.
    expect(previewShares(90, ['a', 'b', 'c'], { a: 0, b: 0, c: 0 })).toEqual({ a: 30, b: 30, c: 30 })
  })

  it('сумма долей всегда равна расходу', () => {
    // Тот же инвариант, что проверяет property-тест в Rust: без него план
    // переводов не закрылся бы в ноль.
    for (const amount of [1, 7, 13, 999, 13700]) {
      const shares = previewShares(amount, four, { c: 1 })
      const total = Object.values(shares).reduce((sum, value) => sum + value, 0)
      expect(total).toBe(amount)
    }
  })
})
```
