# Настройка Neon

Пошаговая инструкция: что сделать в Neon, чтобы можно было выполнять
[план 2](superpowers/plans/2026-08-05-persistence-layer.md). Всё бесплатно, карта не нужна.

Итог, к которому идём: проект с тремя бранчами и файл `backend/.env` с двумя строками подключения.

## Зачем три бранча

Бранч в Neon — это полноценная копия базы, создаваемая мгновенно по принципу copy-on-write. Нам
нужны три, и у каждого своя роль:

| Бранч | Для чего | Кто в него пишет |
| --- | --- | --- |
| `production` | Продакшн | Только задеплоенный на Render бэкенд, позже |
| `dev` | Локальная разработка | Ты, когда запускаешь `cargo run` |
| `test` | Интеграционные тесты | `cargo test`, много раз в минуту |

Тесты пишут и удаляют данные, поэтому у них своя база. Если бы они ходили в `dev`, каждый прогон
затирал бы то, что ты руками навводил, а если бы в `production` — затирал бы реальные встречи друзей.

## Шаг 1. Аккаунт и проект

1. Зайти на [neon.com](https://neon.com) и зарегистрироваться. Проще всего через GitHub — тогда
   не придётся заводить отдельный пароль. Карта на бесплатном плане не требуется.
2. Первым делом Neon предложит создать **организацию** (экран «Welcome to Neon / Let's get your org
   set up»): имя — любое, назначение — `Personal projects`, приглашать никого не надо. Панель справа
   с регионом на этом экране информационная — показывает автоопределённый регион и лимиты плана,
   выбор региона будет дальше.
3. Создать проект. В форме создания:
   - **Name** — `reckoner`.
   - **Postgres version** — оставить предложенную по умолчанию (свежая).
   - **Region** — см. врезку ниже.
4. Neon сразу создаст первый бранч (обычно называется `main` или `production`) и базу внутри него
   (обычно `neondb`). Ничего переименовывать не нужно — просто запомни, как называется первый бранч,
   он и будет продакшном.

### Про регион

**Главное правило: регион Neon и регион Render должны совпадать.** Это важнее, чем близость к тебе:
один запрос к API делает несколько обращений к базе, поэтому задержка между бэкендом и базой
умножается, а твоя задержка до бэкенда — нет. Регион у проекта потом не меняется.

- **Франкфурт (`eu-central-1`)** — предпочтительно: до API будет ~40 мс вместо ~120 мс.
- **Ohio (`us-east-2`)** — если Neon уже зафиксировал его и выбора нет, это не проблема: при деплое
  поставим Render тоже в Ohio. У Render есть оба региона.

## Шаг 2. Создать бранчи `dev` и `test`

В консоли проекта найти раздел **Branches** и создать два бранча, оба от корневого:

1. Кнопка создания бранча → **Name**: `dev`, **Parent branch**: корневой (`main`/`production`).
2. Ещё раз → **Name**: `test`, **Parent branch**: тот же корневой.

Про «Include data up to» / точку во времени: оставляй по умолчанию (текущее состояние). Копировать
нечего — база пока пустая.

После этого в списке должно быть три бранча. На бесплатном плане лимит — 10 бранчей на проект, так
что запас есть.

## Шаг 3. Взять строки подключения — обязательно **unpooled**

Это единственный шаг, где легко ошибиться, и ошибка проявится не сразу, а случайными падениями
запросов.

В консоли есть кнопка **Connect** (в разных версиях интерфейса она называется «Connect» или
«Connection Details»). В открывшемся окне выбираются: **Branch**, **Database**, **Role**.

**Что важно:**

- **Переключатель «Connection pooling» должен быть ВЫКЛЮЧЕН.** Нам нужна прямая строка. Проверить
  легко: в правильной строке в имени хоста **нет** `-pooler`.

  ```
  правильно:  ...@ep-cool-darkness-a1b2c3d4.eu-central-1.aws.neon.tech/neondb?sslmode=require
  неправильно:...@ep-cool-darkness-a1b2c3d4-pooler.eu-central-1.aws.neon.tech/neondb?sslmode=require
  ```

  Почему: pooled-эндпоинт — это PgBouncer в transaction mode. Он выбрасывает подготовленные запросы
  между транзакциями, а наш драйвер (sqlx) по умолчанию их использует, и на случайных запросах
  начинают лететь ошибки `prepared statement "sqlx_s_26" already exists`. Пулер полезен, когда
  подключений тысячи и они короткие; у нас один процесс со своим пулом на пять соединений, так что
  он не нужен и только мешает.

- **Если в строке есть `channel_binding=require` — убери этот параметр.** Оставь только
  `?sslmode=require`. Шифрование от этого не пропадает: `sslmode=require` и есть требование TLS,
  а `channel_binding` — дополнительная привязка канала, поддержку которой на стороне драйвера я
  гарантировать не могу. Если окажется, что она работает, вернём одной правкой.

Нужны две строки:

1. Для бранча **`dev`** — она пойдёт в `DATABASE_URL`.
2. Для бранча **`test`** — она пойдёт в `TEST_DATABASE_URL`.

Строку для корневого бранча брать пока не надо: она понадобится при деплое на Render и там будет
задана в панели, а не в файле.

## Шаг 4. Положить строки в `backend/.env`

Создать файл `backend/.env` (именно внутри `backend/`, не в корне репозитория) и вписать две строки:

```
DATABASE_URL=postgresql://ВАШ_ЮЗЕР:ВАШ_ПАРОЛЬ@ep-xxxx.eu-central-1.aws.neon.tech/neondb?sslmode=require
TEST_DATABASE_URL=postgresql://ВАШ_ЮЗЕР:ВАШ_ПАРОЛЬ@ep-yyyy.eu-central-1.aws.neon.tech/neondb?sslmode=require
```

Формат строгий и простой:

- никаких кавычек вокруг значения;
- никаких пробелов вокруг `=`;
- одна переменная на строку;
- хосты у `dev` и `test` **разные** (`ep-xxxx` и `ep-yyyy` — это разные вычислительные эндпоинты).
  Если они совпали, значит строка скопирована для одного и того же бранча дважды — вернись к шагу 3.

**Файл не попадёт в git:** строка `backend/.env` добавляется в `.gitignore` первым же шагом плана 2.
Но до этого момента он ещё не закрыт, поэтому не делай коммитов, пока я не выполню Task 1. Если
случайно закоммитишь — скажи, пароль в Neon надо будет сбросить, из истории git его так просто
не вычистить.

## Шаг 5. Проверить, что всё живо

В консоли Neon есть **SQL Editor**. Выбери бранч `dev` и выполни:

```sql
select current_database(), version();
```

Ожидается: имя базы и версия Postgres. Повтори для бранча `test`.

Больше проверять пока нечем — таблиц нет, их создаст миграция из плана 2. Подключение из Rust я
проверю первым делом, когда начнём: если строка скопирована неверно, сервер упадёт на старте
с внятным сообщением, а не будет отдавать 500 на каждый запрос.

## Что стоит знать про бесплатный план

**Компьют засыпает через 5 минут простоя.** Первый запрос после сна ждёт пробуждения — обычно
меньше секунды, иногда пару секунд. На бесплатном плане это нормально и на счётчик компьют-часов
время сна не идёт: простаивающая база не тратит квоту.

**Лимиты:** 0.5 ГБ хранилища на проект, 100 компьют-часов на проект в месяц, до 10 бранчей.
Для нашего случая это очень много: обложки встреч по ~300 КБ, то есть на полтысячи встреч хватит
только по хранилищу, а компьют-часы при трёх друзьях не закончатся никогда.

**Бесплатный план бессрочный,** не триальный — база не удалится через 30 дней. Это была одна из
причин выбрать Neon, а не бесплатный Postgres на Render, который именно так и делает.

**Пароль виден только при создании.** Если потерял — в консоли есть сброс пароля роли; после сброса
надо будет обновить обе строки в `.env`.

## Если что-то пошло не так

| Симптом | Причина |
| --- | --- |
| `prepared statement "sqlx_s_N" already exists` | взята pooled-строка; убери `-pooler` из хоста |
| Ошибка аутентификации при верных логине и пароле | в строке остался `channel_binding=require`; убери |
| `TEST_DATABASE_URL не задана` при `cargo test` | нет второй строки в `backend/.env` |
| Тесты затирают данные, которые ты вводил руками | обе строки указывают на один бранч; сверь хосты |
| Долгий первый запрос после паузы | компьют просыпается, это ожидаемо |

Когда закончишь — скажи, и я начну выполнять план 2 с первой задачи: закрою `.env` от git и подключу
sqlx.
