# Handoff: Сплитер расходов на встречах (Meetup Expense Splitter)

## Overview
Адаптивное веб-приложение (Desktop / Android / iOS, один responsive-лейаут) для учёта денег на дружеских встречах. Пользователь без авторизации видит список всех встреч, заходит внутрь, добавляет участников и расходы, а приложение само считает минимальный набор переводов, которые закроют встречу «по нулям».

Ключевые сценарии:
1. Список встреч → поиск, фильтр по участнику, сортировка, статус закрытости встречи цветом.
2. Страница встречи → обложка, заголовок, описание, сводка, участники, история операций, блок «кто кому должен» (3 представления), лог изменений.
3. Модальные окна: новая встреча, добавить/редактировать/удалить участника, добавить расход (с долями), добавить перевод.

## About the Design Files
Файлы в этом бандле — **дизайн-референс, сделанный в HTML**. Это прототип, показывающий предполагаемый вид и поведение, а **не продакшн-код для копирования**. Задача — воспроизвести эти экраны в существующем окружении целевого проекта (React / Vue / Next / SwiftUI / нативный клиент — что уже используется), опираясь на его паттерны, роутинг, стейт-менеджмент и библиотеку компонентов. Если окружения ещё нет — выбрать подходящий стек и реализовать дизайн в нём.

Прототип хранит данные в `localStorage`; в реальной реализации это API + БД (см. «Data model & API»).

## Fidelity
**High-fidelity.** Цвета, типографика, отступы, радиусы и состояния — финальные, ниже приведены точные значения. Вся расчётная логика (сплит по долям, минимизация переводов, балансы) в прототипе работает по-настоящему и является спецификацией поведения — переносить её надо один-в-один, но на сервер.

## Interactions & Behavior
- **Навигация:** список ⇄ страница встречи. В проде — роуты `/` и `/meetings/:id` (в прототипе это состояние).
- Клик по карточке встречи открывает встречу; клик по логотипу или «← Все встречи» возвращает.
- Все изменения (участник, расход, перевод, удаление, «Отдал») **немедленно** пересчитывают балансы, план переводов, статус и статкарточки — без перезагрузки.
- Удаление участника удаляет и все записи, где он плательщик или получатель.
- Валидация: сумма должна парситься (`,` и пробелы допускаются) и быть > 0, иначе submit игнорируется; имя не должно быть пустым; в переводе отправитель ≠ получатель; описание расхода по умолчанию «Без описания».
- Hover-состояния описаны выше по каждому элементу; фокус на инпутах — `outline: none` + существующая граница (в проде добавить видимый focus-ring для доступности).
- **Адаптив:** нет медиазапросов — всё на `auto-fit`/`auto-fill` grid, `flex-wrap` и `clamp()` для типографики. На ~360 px все сетки схлопываются в одну колонку, фильтры переносятся, таблица долгов скроллится горизонтально. Хит-таргеты кнопок ≥ 40 px.

## State Management
Клиентское состояние прототипа:
- `view: 'list' | 'meeting'`, `meetingId`
- `query`, `sort`, `person` — фильтры списка
- `tab: 'people' | 'table' | 'balance'` — представление долгов
- `expanded: { [participantId]: boolean }` — раскрытые должники (по умолчанию раскрыты)
- `modal: null | 'meeting' | 'person' | 'editPerson' | 'expense' | 'transfer'`, `form: {...}` — включая `excl: { [participantId]: 0|0.25|0.5|0.75|1 }`

Производные значения считаются на каждый рендер: `balances`, `settle`, `totalOf`, суммы «внёс». В проде: считать на сервере при чтении встречи (или мемоизировать на клиенте), фильтры/сортировку списка — на сервере.

## Data model & API (предлагаемое)
```
Meeting   { id, title, description, emoji, coverUrl, date, createdAt }
Participant { id, meetingId, name, emoji, color }
Entry     { id, meetingId, type: 'expense'|'transfer', payerId, toId|null,
            amount: number, description, createdAt,
            exclusions: { [participantId]: 0..1 } }   // доля, НЕ учитываемая для участника
LogRecord { id, meetingId, text, createdAt }
```
Эндпоинты: `GET /meetings?q&participant&sort`, `POST /meetings`, `GET /meetings/:id`,
`POST|PATCH|DELETE /meetings/:id/participants[/:pid]`, `POST|DELETE /meetings/:id/entries[/:eid]`,
`POST /meetings/:id/cover`.

### Алгоритм расчёта (перенести один-в-один)
1. **Доли расхода.** Для расхода вес участника `w_i = max(0, 1 − exclusion_i)` (по умолчанию 1). Если сумма весов = 0 — считаем всех по 1. Доля участника `= amount × w_i / Σw`.
2. **Баланс.** `net_i = Σ(расходы, оплаченные i) + Σ(переводы, отправленные i) − Σ(переводы, полученные i) − Σ(доли i по всем расходам)`.
3. **План переводов.** Округлить `net` до рублей. Должники (`net < −0.5`) и кредиторы (`net > 0.5`) сортируются по убыванию модуля; жадно сводим наибольшего должника с наибольшим кредитором на `min(долг, кредит)` — получаем минимальный по количеству список переводов. Переводы < 0.5 ₽ отбрасываются.
4. **Статус встречи** = длина плана: 0 → зелёный «Все в расчёте», 1–2 → жёлтый, ≥3 → красный.

Форматирование сумм: `Intl.NumberFormat('ru-RU')` + « ₽», округление до целых рублей. Даты: `ru-RU`, «14 июля» на карточках, `дд.мм чч:мм` в истории и логе.
