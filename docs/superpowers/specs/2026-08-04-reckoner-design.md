# Reckoner — дизайн приложения «Финальная расплата»

Дата: 2026-08-04

## Что это

Адаптивное веб-приложение (PWA; Desktop / Android / iOS одним responsive-лейаутом) для учёта
денег на дружеских встречах. Авторизации нет. Любой посетитель видит список всех встреч,
заходит внутрь, добавляет участников и расходы, а приложение считает минимальный набор
переводов, которые закрывают встречу в ноль.

Дизайн интерфейса задан заранее и лежит в `docs/design/`:

- `handoff.md` — хендофф из Claude Design: токены, экраны, тексты, поведение. **Источник истины
  по внешнему виду.**
- `meetup-splitter.dc.html` + `support.js` — HTML-прототип. Спецификация поведения; открывается
  в браузере, в кодовую базу не переносится.
- `screens/01..05*.png` — пять скриншотов финального вида.

Спека ниже описывает, как это реализуется на нашем стеке, и фиксирует решения, которых в
хендоффе нет либо которые мы сознательно от него отклонили.

### Предварительные условия окружения

**Node.js на машине не установлен** (нет ни `node`, ни `npm`, `frontend/node_modules` и
`frontend/dist` отсутствуют — скаффолд собирался в песочнице Cowork и был синхронизирован
файлами). Без Node фронтенд нельзя ни собрать, ни запустить, ни протестировать. Установка Node
LTS — первый шаг реализации.

Docker, локального Postgres и `sqlite3` тоже нет. Поэтому база для разработки и тестов —
облачный Neon (см. «Окружения»), а доменная логика спроектирована так, чтобы её тесты не
требовали ни базы, ни сети.

## Топология деплоя

| Часть | Где | Почему |
| --- | --- | --- |
| Фронтенд | GitHub Pages | Бесплатно и бессрочно, всегда быстрая отдача статики |
| Бэкенд | Render, free web service | Бесплатно, поддерживает Rust, есть env vars и TLS |
| База | Neon, free plan | Бессрочный бесплатный Postgres, 0.5 ГБ, scale-to-zero |

Отвергнутые варианты:

- **Всё на одном хосте** (Axum раздаёт и API, и статику) — проще в настройке, но холодный старт
  Render ударил бы по загрузке самой страницы: белый экран на 30–60 с вместо мгновенной статики.
- **Cloudflare Workers + D1** — нет холодных стартов, но Rust компилируется в WASM, `sqlx`/`tokio`
  не работают, нужен другой код доступа к данным. Высокий риск потратить время на инфраструктуру.
- **Без бэкенда, данные в `localStorage`** — дало бы 100 % GitHub Pages, но данные остались бы в
  браузере одного человека, и друзья не увидели бы общих встреч. Ломает суть задачи.
- **Бесплатный Postgres на Render** — удаляется через 30 дней после создания. Непригоден.
- **Koyeb** — бесплатный compute закрыт в 2026.

Следствия, которые надо учесть в реализации:

1. Фронт и API на разных origin → нужен настоящий CORS (см. «Безопасность») и `VITE_API_BASE_URL`
   вместо дев-прокси в проде.
2. Pages отдаёт сайт из подпапки → `base: '/reckoner/'` и SPA-фолбэк `404.html`.
3. Render засыпает через 15 минут простоя → отдельное состояние «будим сервер» в UI.

## Архитектура бэкенда: тонкий сервер, расчёт на чтении

В базе лежат **только факты**: встречи, участники, записи, доли, лог. Ничего производного не
хранится. Вся математика — отдельный модуль `backend/src/domain/`, который не знает ни про
`sqlx`, ни про HTTP: на вход обычные структуры, на выход доли, балансы, план переводов, статус.

Почему так: расчёт нужен не только на странице встречи — на списке встреч цвет карточки и
сортировка «Сначала незакрытые» тоже зависят от числа оставшихся переводов, то есть сервер
обязан уметь считать сплит для каждой встречи в списке. При десятках встреч это микросекунды в
памяти. Взамен получаем единственное место, где живёт денежная логика, и это чистая функция,
покрываемая быстрыми тестами без инфраструктуры.

Отвергнуто:

- **Хранить производное в БД** (балансы и число переводов в таблице встреч, обновление на
  записи) — быстрее список, но появляется производное состояние, обязанное сходиться с фактами,
  и миграции при любой правке формулы. Преждевременная оптимизация под нагрузку, которой не будет.
- **Считать на клиенте** — алгоритм оказался бы не там, где он описан, а для покраски карточек
  списка пришлось бы тянуть на клиент все записи всех встреч.

Единственное, что считается на клиенте, — живое превью долей в модалке расхода (сумма на
каждого обновляется по мере ввода). Это не алгоритм сплита, а формула `amount × вес / Σвес`;
дублирования логики нет.

## Деньги и алгоритм

### Целые рубли, никаких копеек

Суммы вводятся, хранятся, считаются и отображаются **только в целых рублях** (`bigint`). Ввод
дробной части не принимается: заставлять друзей переводить друг другу 37 копеек бессмысленно.
Плавающей точки в денежном пути нет нигде — прототип использует `float`, мы этого не переносим.

### Доли

Доля участника в расходе — одно из пяти значений: `1, ¾, ½, ¼, 0`. Храним числитель четвертей
как целое `0..4`. Клик по чипу в модалке циклит `1 → ¾ → ½ → ¼ → 0 → 1`.

В БД пишем **только неполные доли**: если расход делится на всех поровну, таблица долей для него
пуста, отсутствие строки означает долю 1.

### Расчёт долей: целочисленно, остаток по наибольшей дробной части

Пусть у расхода сумма `A` рублей и веса участников `w_i` в четвертях (`0..4`), `W = Σw_i`.
Участник, у которого нет строки в `entry_shares`, имеет вес `4` — полную долю.

1. Если `W == 0` — считаем всех по 1 (поведение прототипа: расход, из которого исключили всех,
   делится на всех поровну).
2. Целая часть доли: `base_i = (A × w_i) / W` (целое деление, умножение в `i128`).
3. Остаток `R = A − Σbase_i` рублей раздаём по одному рублю участникам с наибольшим
   `(A × w_i) mod W`. При равенстве остатков — по `position` участника, чтобы результат был
   детерминированным.

Это **сознательное отклонение от прототипа**. Там доля считается как `amount × w / Σw` во
`float`, и сумма долей не обязана в точности равняться расходу. Инвариант «сумма балансов равна
нулю» держится именно на этом равенстве, а на нём в свою очередь держится способность жадного
алгоритма закрыть встречу в ноль. Целочисленная раздача по остатку гарантирует
`Σ долей == A` точно. Видимые цифры совпадают с прототипом; 100 ₽ на трёх дают 34 / 33 / 33.

### Баланс

Для каждого участника `i`:

```
net_i = Σ(расходы, оплаченные i)
      + Σ(переводы, отправленные i)
      − Σ(переводы, полученные i)
      − Σ(доли i по всем расходам)
```

Всё в целых рублях, поэтому `Σ net_i == 0` выполняется точно.

### План переводов

1. Должники (`net < 0`) и кредиторы (`net > 0`) сортируются по убыванию модуля.
2. Жадно сводим наибольшего должника с наибольшим кредитором на `min(долг, кредит)`, пока
   должники не кончатся.
3. Переводы на 0 ₽ не попадают в план.

Даёт минимальный по количеству список переводов. Пороги `< −0,5 ₽` / `> 0,5 ₽` из хендоффа
превращаются в `< 0` / `> 0`: в целых рублях округлять нечего. Оговорка хендоффа про возможное
расхождение плана с точным долгом на пару рублей **не применяется** — план закрывает встречу
ровно в ноль.

### Статус встречи

По длине плана: `0` → зелёный «Все в расчёте»; `1–2` → жёлтый «Осталось N»; `≥3` → красный
«Осталось N»; нет участников → «Нет участников».

### Модуль `domain`

```
backend/src/domain/
  mod.rs        публичные типы: MeetingFacts, ParticipantId, Transfer, MeetingStatus
  shares.rs     доли одного расхода
  balance.rs    net по всем участникам
  settle.rs     план переводов
  status.rs     статус по длине плана
```

Чистые функции, никаких зависимостей от `sqlx`, Axum и времени. Пишутся через TDD.

## Модель данных

Postgres. Идентификаторы — `uuid` (`gen_random_uuid()`).

```sql
meetings
  id               uuid    primary key default gen_random_uuid()
  title            text    not null
  description      text    not null default ''
  emoji            text    not null default '✨'
  held_on          date    not null                 -- дата самой встречи
  cover_mime       text
  cover_bytes      bytea
  cover_version    integer not null default 0       -- инкремент при замене, сбрасывает кэш
  created_at       timestamptz not null default now()
  updated_at       timestamptz not null default now()

participants
  id            uuid     primary key default gen_random_uuid()
  meeting_id    uuid     not null references meetings(id) on delete cascade
  name          text     not null
  emoji         text     not null
  color_index   smallint not null                   -- индекс в палитре аватаров
  position      integer  not null                    -- порядок добавления
  created_at    timestamptz not null default now()
  unique (meeting_id, position)

entries
  id              uuid    primary key default gen_random_uuid()
  meeting_id      uuid    not null references meetings(id) on delete cascade
  kind            text    not null check (kind in ('expense','transfer'))
  payer_id        uuid    not null references participants(id) on delete cascade
  recipient_id    uuid             references participants(id) on delete cascade
  amount_rubles   bigint  not null check (amount_rubles > 0)
  description     text    not null default ''
  occurred_at     timestamptz not null default now()
  created_at      timestamptz not null default now()
  check ((kind = 'transfer') = (recipient_id is not null))
  check (recipient_id is null or recipient_id <> payer_id)

entry_shares                                        -- только неполные доли
  entry_id         uuid     not null references entries(id) on delete cascade
  participant_id   uuid     not null references participants(id) on delete cascade
  weight_quarters  smallint not null check (weight_quarters between 0 and 3)
  primary key (entry_id, participant_id)

meeting_log
  id           bigserial   primary key
  meeting_id   uuid        not null references meetings(id) on delete cascade
  text         text        not null
  created_at   timestamptz not null default now()
```

Индексы: `entries(meeting_id, occurred_at desc)`, `meeting_log(meeting_id, created_at desc)`.
Отдельный индекс по `participants(meeting_id)` не нужен — его роль выполняет уникальный индекс
по `(meeting_id, position)`.

Про `unique (meeting_id, position)`. Ограничение не косметическое: `position` участвует в
тай-брейке при раздаче остатка рублей (см. «Расчёт долей»), и если два участника одной встречи
получат одинаковый `position`, результат начнёт зависеть от порядка строк, который Postgres при
равных ключах сортировки не гарантирует — два одинаковых запроса могли бы показать, что лишний
рубль платят разные люди. Домен со своей стороны тоже подстрахован (третий ключ сортировки — `id`),
но полагаться на это как на единственную защиту неправильно.

`position` присваивается как **`max(position) + 1`** по встрече, а не как число уже существующих
участников. Разница принципиальная. Со счётчиком по количеству удаление участника из середины
привело бы к выдаче уже занятого номера: добавили двоих (0 и 1), удалили первого, осталcя один —
`count(*) = 1`, и следующий получил бы позицию 1, которая занята. Это проверено на живой базе:
Postgres отвечает `duplicate key value violates unique constraint
"participants_meeting_id_position_key"`, то есть добавление участника ломалось бы после любого
удаления. Монотонный счётчик оставляет в нумерации дырки — они безобидны, потому что важен только
порядок, а не плотность.

Каскады реализуют требование хендоффа «удаление участника удаляет и все записи, где он
плательщик или получатель»: `on delete cascade` на `payer_id` и на `recipient_id`.

Цвет участника в БД не хранится — только `color_index`; палитру знает фронтенд. То же для
градиентов обложек-фолбэков: индекс карточки, палитра на клиенте.

## API

Плоский REST под `/api`. JSON, `camelCase` в телах.

**Каждый мутирующий запрос возвращает целиком пересчитанную встречу** — в том же виде, что и
`GET /api/meetings/:id`. Это убирает лишний round-trip и делает рассинхронизацию UI невозможной.

```
GET    /api/health

GET    /api/meetings?q=&participant=&sort=
POST   /api/meetings
GET    /api/meetings/:id
PATCH  /api/meetings/:id
DELETE /api/meetings/:id

GET    /api/meetings/:id/cover
PUT    /api/meetings/:id/cover
DELETE /api/meetings/:id/cover

POST   /api/meetings/:id/participants
PATCH  /api/meetings/:id/participants/:pid
DELETE /api/meetings/:id/participants/:pid

POST   /api/meetings/:id/entries
PATCH  /api/meetings/:id/entries/:eid
DELETE /api/meetings/:id/entries/:eid
```

### `GET /api/meetings`

Поиск, фильтр и сортировка — на сервере.

- `q` — подстрока, регистронезависимо, по названию и описанию.
- `participant` — имя участника; встреча попадает в выдачу, если такой участник в ней есть.
- `sort` — `date-desc` (по умолчанию), `date-asc`, `total-desc`, `open-first`
  (по числу оставшихся переводов, убывание).

Ответ — массив карточек:

```json
{
  "id": "uuid", "title": "Дача у Влада", "description": "…", "emoji": "🏡",
  "heldOn": "2026-07-23", "hasCover": true, "coverVersion": 3,
  "totalRubles": 13700,
  "participants": [{ "id": "uuid", "name": "Настя", "emoji": "🦊", "colorIndex": 1 }],
  "pendingTransfers": 3,
  "status": "alarm"
}
```

`status`: `settled` | `attention` | `alarm` | `no-participants`.

### `GET /api/meetings/:id`

```json
{
  "id": "uuid", "title": "…", "description": "…", "emoji": "🏡",
  "heldOn": "2026-07-23", "hasCover": true, "coverVersion": 3,
  "createdAt": "2026-07-23T19:00:00Z",
  "participants": [
    { "id": "uuid", "name": "Настя", "emoji": "🦊", "colorIndex": 1, "position": 0,
      "contributedRubles": 3200, "netRubles": -225 }
  ],
  "entries": [
    { "id": "uuid", "kind": "expense", "payerId": "uuid", "recipientId": null,
      "amountRubles": 8400, "description": "Продукты на все дни",
      "occurredAt": "2026-07-23T20:00:00Z",
      "shares": [{ "participantId": "uuid", "weightQuarters": 2 }],
      "sharedByAll": false }
  ],
  "settlement": [{ "fromId": "uuid", "toId": "uuid", "amountRubles": 3425 }],
  "totals": { "spentRubles": 13700, "perPersonRubles": 3425, "pendingTransfers": 3 },
  "status": "alarm",
  "log": [{ "id": 12, "text": "Настя добавляет расход «Продукты на все дни» — 8 400 ₽",
            "createdAt": "2026-07-23T20:00:00Z" }]
}
```

`entries` отсортированы по `occurred_at`, новые сверху. `log` — последние 12 записей, новые
сверху. `sharedByAll: false` означает, что у кого-то доля меньше 1 — фронт по этому флагу
приписывает « · делят не все».

Определения полей, чтобы не разошлись с прототипом:

- `contributedRubles` — подпись «внёс N ₽» в карточке участника. Это **только сумма расходов,
  которые человек оплатил**; отправленные переводы сюда не входит (сверено с прототипом,
  `meetup-splitter.dc.html:630`).
- `netRubles` — баланс из раздела «Деньги и алгоритм». Может быть отрицательным.
- `totals.perPersonRubles` — `spentRubles / число участников`, целочисленно. Если участников нет,
  отдаём `0` (делить не на что).
- `totals.pendingTransfers` — длина `settlement`.

### Тела запросов

| Ручка | Тело |
| --- | --- |
| `POST /meetings` | `{ title, description?, emoji?, heldOn? }` — пустое название → «Новая встреча», `emoji` по умолчанию `✨`, `heldOn` по умолчанию сегодня |
| `PATCH /meetings/:id` | `{ title?, description?, emoji?, heldOn? }` |
| `POST /participants` | `{ name, emoji }` — `colorIndex` и `position` присваивает сервер |
| `PATCH /participants/:pid` | `{ name?, emoji? }` |
| `POST /entries` | `{ kind, payerId, recipientId?, amountRubles, description?, occurredAt?, shares? }` |
| `PATCH /entries/:eid` | те же поля, все опциональные |
| `PUT /cover` | тело — байты картинки, `Content-Type: image/*` |

`shares` — массив `{ participantId, weightQuarters }` только для неполных долей.

Кнопка «Отдал» в блоке долгов — это обычный `POST /entries` с `kind: "transfer"` на предложенную
планом сумму. Отдельной ручки нет.

### Ошибки

`422` с телом `{ "error": "validation", "field": "amountRubles", "message": "…" }` — на
нарушение правил. `404` — нет встречи/участника/записи. `413` — обложка больше 1 МБ.
`415` — не картинка. `500` — всё прочее, без утечки деталей в тело.

Правила валидации (сервер — источник истины, клиент дублирует для мгновенной реакции):

- сумма — целое `> 0`;
- имя участника — непустое после `trim`;
- у перевода `recipientId` обязателен и `≠ payerId`; у расхода — отсутствует;
- описание расхода по умолчанию «Без описания»;
- `payerId` / `recipientId` / `shares[].participantId` должны принадлежать этой встрече;
- `weightQuarters` принимается в диапазоне `0..4`; строки со значением `4` (полная доля) сервер
  не сохраняет — отсутствие строки и есть полная доля. `shares` у перевода запрещены.

## Тексты без рода

У участника нет поля пола, и заводить его ради подписей незачем. При этом в хендоффе есть три
места, где текст приклеен к конкретному имени и потому ломается на женских именах. Везде берём
формулировки, не маркирующие род.

**1. Лог «Что менялось» — настоящее время.** Демо-данные прототипа говорят
«Настя **добавила** расход», а код генерирует `имя + ' добавил расход '`, то есть вывел бы
«Настя добавил». Настоящее время в русском род не маркирует.

**2. Строка баланса в карточке участника.** Прототип (`meetup-splitter.dc.html:636`) даёт
`net > 0 → 'ему должны N ₽'`, `net < 0 → 'должен N ₽'` — на скриншоте `02-meeting-header.png`
это видно как «Настя … должен 225 ₽». Заменяем:

| Баланс | Хендофф | У нас | Цвет |
| --- | --- | --- | --- |
| `> 0` | `ему должны N ₽` | `должны N ₽` | `#25693E` |
| `< 0` | `должен N ₽` | `долг N ₽` | `#C3402E` |
| `= 0` | `в расчёте` | `в расчёте` | `#8B8577` |

**3. Кнопка «Отдал»** в блоке долгов (`meetup-splitter.dc.html:230`) — это действие конкретного
человека, «Настя … Отдал». Заменяем на **«Отдано»**: то же слово, тот же смысл, рода нет.

Обезличенные тексты хендоффа не трогаем: заголовок «Кто кому должен» и подпись «Слева — кто
должен, справа — кому должны» ни к какому имени не привязаны.

### Записи лога

Пишется на сервере в **той же транзакции**, что и сама правка, — так он не может разойтись с
данными. Отдаётся 12 последних записей.

| Событие | Текст |
| --- | --- |
| Создание встречи | `Встреча создана` |
| Правка встречи | `Встреча отредактирована` |
| Смена обложки | `Обновлена обложка встречи` |
| Удаление обложки | `Обложка удалена` |
| Новый участник | `Настя присоединяется к встрече` |
| Правка участника | `Профиль участника обновлён: Настя` |
| Удаление участника | `Участник удалён: Егор` |
| Расход | `Настя добавляет расход «Продукты» — 8 400 ₽` |
| Перевод | `Настя переводит 3 425 ₽ → Влад` |
| Правка записи | `Запись изменена: 8 400 ₽` |
| Удаление записи | `Удалена запись на 2 100 ₽` |

Кнопки «Отдано» в блоке долгов в этой таблице нет намеренно: это обычный `POST /entries`
с `kind: "transfer"`, и сервер не отличает его от перевода, введённого руками. Текст у обоих
один — «переводит».

## Фронтенд

### Роутинг

`react-router-dom`, два роута: `/` (список) и `/meetings/:id` (встреча).

GitHub Pages отдаёт сайт из подпапки → `base: '/reckoner/'` в Vite, в CI после сборки
`dist/index.html` копируется в `dist/404.html` (штатный SPA-фолбэк для Pages; без него прямая
ссылка на встречу отдаст 404). Чистые URL выбраны, чтобы ссылку на конкретную встречу можно было
кинуть в чат. Если Pages конфликтует с service worker'ом — переключение на hash-роутинг
локализовано в одном месте.

### Данные

TanStack Query. Мы сознательно отказались от WebSocket (см. «Отложено»), а refetch при возврате
фокуса, дедупликация запросов и инвалидация кэша после мутации — ровно то, что нужно взамен.
Поскольку мутация возвращает пересчитанную встречу целиком, её ответ кладётся прямо в кэш;
дополнительного запроса нет.

Оптимистичных обновлений не делаем: кнопка на время запроса показывает загрузку.
Рассинхронизироваться нечему.

### Стили

CSS Modules плюс один `styles/tokens.css` с кастомными свойствами, перенесёнными напрямую из
таблицы токенов `docs/design/handoff.md`. Tailwind отвергнут: в дизайне значения вида `14.5px`,
`12.5px`, `1.5px` воюют со шкалой Tailwind, каждое пришлось бы прописывать в конфиг руками, а с
CSS-переменными соответствие спеке проверяется глазами по таблице.

Адаптив — как в хендоффе: без медиазапросов, на `auto-fit`/`auto-fill` grid, `flex-wrap` и
`clamp()`. Хит-таргеты ≥ 40 px. Таблица долгов скроллится горизонтально.

Доступность: в прототипе на инпутах `outline: none` — добавляем видимый focus-ring.

### Шрифты

Onest (400/500/600/700), Unbounded (600/700), JetBrains Mono (500/700) — self-host через
`@fontsource`, не Google Fonts: это PWA, она должна работать в офлайне и не ходить за отрисовкой
текста на сторонний домен. Сабсет — кириллица и латиница.

### Холодный старт Render

Render засыпает через 15 минут простоя, первый запрос после сна висит 30–60 с. По умолчанию друг
увидит белый экран и решит, что сайт сломался. Поэтому: на старте приложения дёргаем
`GET /api/health`; если ответа нет через ~2 с — показываем экран «будим сервер, это займёт около
минуты» со спиннером. Запрос не отменяем, агрессивных таймаутов не ставим.

## Обложки встреч

`bytea` в Postgres, без внешнего хранилища: на бесплатном Render нет постоянного диска, а
поднимать S3/R2 ради нескольких фотографий — лишняя сущность.

- Клиент перед отправкой уменьшает картинку через canvas: не больше 1600 px по большей стороне,
  JPEG q0.82, потолок ~500 КБ.
- Сервер отбивает тело больше 1 МБ (`413`) и не-картинки (`415`).
- `GET /api/meetings/:id/cover` отдаёт байты с `ETag` и
  `Cache-Control: public, max-age=31536000, immutable`; `coverVersion` в query-параметре сбрасывает
  кэш при замене.
- 0,5 ГБ Neon хватит на тысячу с лишним встреч.

Загрузка — drag & drop в зону обложки, как в дизайне, плюс клик по зоне открывает файловый диалог
(в прототипе только drop; на телефоне бросить файл нечем).

## Окружения

Neon free даёт до 10 бранчей, используем три:

| Бранч | Для чего |
| --- | --- |
| `production` | Продакшн (Render) |
| `dev` | Локальная разработка |
| `test` | Интеграционные тесты |

Локально: терминал 1 — `cd backend && cargo run` (читает `DATABASE_URL` из `.env`, не в git);
терминал 2 — `cd frontend && npm run dev` (дев-прокси `/api` → `localhost:3000`, `VITE_API_BASE_URL`
в дев-режиме пустой).

Миграции — встроенный `sqlx::migrate!`, применяются при старте приложения. Инстанс один,
отдельный шаг в деплое не нужен.

## Безопасность

Авторизации нет — это осознанное требование: список всех встреч видит любой посетитель, и любой
может править любую встречу. Соответственно:

- CORS сужаем с текущего `allow_origin(Any)` до origin наших GitHub Pages из переменной
  `ALLOWED_ORIGIN`. Открытый CORS для прода не оставляем.
- Ограничение размера тела запроса на всех ручках.
- Все параметры — через связывание в `sqlx`, никакой склейки SQL.
- `DATABASE_URL` только в переменных окружения; `.env` в `.gitignore`.

## CI / CD

Два workflow GitHub Actions.

**`ci.yml`** — на pull request и push: `cargo fmt --check`, `cargo clippy -D warnings`,
`cargo test` (доменные тесты, без базы), `tsc -b`, `oxlint`, `npm run build`.

**`pages.yml`** — на push в основную ветку: сборка фронта с `VITE_API_BASE_URL` из repo variable,
копирование `dist/index.html` → `dist/404.html`, публикация через `actions/deploy-pages`.

Бэкенд — `render.yaml` в репозитории, автодеплой Render из основной ветки. Переменные:
`DATABASE_URL` (**unpooled**-строка Neon, без `-pooler` в хосте), `ALLOWED_ORIGIN`,
`PORT` (даёт Render).

Про unpooled: pooled-эндпоинт Neon — это PgBouncer в transaction mode, который выбрасывает
подготовленные запросы между транзакциями, а `sqlx` по умолчанию их использует, и на случайных
запросах начинают лететь ошибки `prepared statement "sqlx_s_N" already exists`. Пулер решает задачу
тысяч короткоживущих подключений (serverless-функции); у нас один долгоживущий процесс со своим
пулом на пять соединений, поэтому он не нужен. Из строки также убирается `channel_binding=require`:
TLS обеспечивает `sslmode=require`, а поддержку привязки канала на стороне драйвера мы не
проверяли.

## Тесты

**Юнит-тесты домена — основа.** Не требуют ни базы, ни сети. Домен пишется через TDD: ожидаемое
поведение задано этой спекой заранее.

Кейсы:

- Три демо-встречи из прототипа как фикстуры с точными ожидаемыми планами переводов
  («Солевые шашлыки» — 5 участников без расходов; «Дача у Влада» — жёлтый статус, 3 перевода;
  «Кино и шаурма» — закрыта в ноль).
- Ноль участников.
- Один участник.
- У всех доля 0 → по спеке считаем всех по 1.
- Неделимое деление: 100 ₽ на трёх → 34 / 33 / 33.
- Неполные доли: 100 ₽ при весах `1, ½, ½` → 50 / 25 / 25.
- Перевод больше долга (уводит баланс в другую сторону).
- Удаление участника посреди истории.
- Property-тест (`proptest`): на случайных наборах участников, расходов и долей
  `Σ net == 0` и план всегда сводит все балансы в ноль. Именно этот инвариант гарантирует, что
  жадный алгоритм закроет встречу.

**Интеграционные тесты хендлеров** — против `test`-бранча Neon, каждый в транзакции с откатом.
Покрывают ручки, валидацию (422) и каскады: удалили участника — исчезли записи, где он плательщик
или получатель.

**Фронтенд** — Vitest для `format.ts` и `sharePreview.ts`. Тяжёлых компонентных тестов не будет:
ценность в денежной математике, а она в Rust.

**Ручная сверка** — чек-лист по пяти скриншотам из `docs/design/screens/` плюс модальные окна
(скриншотов модалок в хендоффе нет, они описаны текстом в разделе 4 `handoff.md`).

## Отклонения от хендоффа

| Что | Как в хендоффе | Как у нас | Почему |
| --- | --- | --- | --- |
| Доли расхода | `float`, сумма долей может не равняться расходу | целые рубли, остаток по наибольшей дробной части | инвариант `Σ net == 0`, без него план может не закрыться в ноль |
| Пороги отсечения | `< −0,5 ₽` / `> 0,5 ₽`, округление `net` до рублей | `< 0` / `> 0` | в целых рублях округлять нечего |
| Тексты лога | прошедшее время, род не сходится с именем | настоящее время | «Настя добавил» — баг; поля пола нет |
| Баланс в карточке участника | `ему должны N ₽` / `должен N ₽` | `должны N ₽` / `долг N ₽` | то же: «Настя должен» на скриншоте |
| Кнопка в блоке долгов | `Отдал` | `Отдано` | то же: «Настя … Отдал» |
| Загрузка обложки | только drag & drop | плюс клик по зоне | на телефоне бросить файл нечем |
| Фокус на инпутах | `outline: none` | видимый focus-ring | доступность; хендофф сам это и просит |
| Шрифты | Google Fonts | self-host `@fontsource` | офлайн в PWA, без стороннего домена |
| Градиент обложки | по индексу карточки в списке | по хешу `id` встречи | при смене сортировки у встречи менялась картинка |
| Время в истории и логе | `дд.мм чч:мм` в тексте хендоффа | `дд.мм, чч:мм` | на скриншотах 03 и 04 запятая есть в обоих местах, а они high-fidelity |
| Кнопка «Отдано» | сразу создаёт перевод | открывает модалку с подставленными сторонами и суммой | сумма бывает не круглой, а отменить перевод можно только удалением записи |
| Правка перевода | — | только удалить и завести заново | полей у перевода три, отдельная форма правки не окупается; у расхода правка есть — там теряется разбивка по долям |
| `ETag` обложки | не оговорён | номер версии, а не хеш байтов | хеш пришлось бы считать на каждый запрос, а версия меняется ровно когда меняется картинка |
| Тип загружаемой обложки | не оговорён | определяется по первым байтам, `Content-Type` игнорируется | заголовок присылает клиент, и доверять ему — значит не проверять вовсе |
| Стопка аватаров | максимум 5, остальные не показаны | пятеро плюс чип «+N» | встреча на девятерых выглядела как встреча на пятерых |

## Добавлено к хендоффу

Операции, которых в дизайне нет, но без них приложение неудобно:

1. **Удаление встречи** — `DELETE /meetings/:id`, кнопка «Удалить» в модалке правки встречи (как у
   участника), с подтверждением. Иначе опечатка или тестовая запись остаётся в списке навсегда.
2. **Редактирование встречи** — название, описание, эмодзи. В дизайне есть только создание и смена
   обложки, причём новая встреча всегда рождается с эмодзи `✨`, и поменять его негде.
3. **Дата встречи отдельным полем** — `held_on`. В прототипе дата на карточке равна моменту
   создания записи: шашлыки в субботу, а встречу завели в среду → на карточке среда. Поле в
   модалке, по умолчанию сегодня.
4. **Редактирование расхода и перевода** — `PATCH /entries/:eid`. В дизайне запись можно только
   удалить крестиком и завести заново, теряя разбивку по долям.

## Отложено

- **WebSocket / живые обновления.** В скаффолде лежит эхо-заглушка `GET /api/ws` — **убираем**.
  Вместо realtime — перезапрос после своей правки и при возврате фокуса; для 3–5 друзей этого
  достаточно. На засыпающем Render WS-соединения всё равно рвались бы, и пришлось бы писать
  реконнект с backoff ради редкого сценария.
- **Авторизация.** Требование задачи — её нет.
- **Мультивалютность.** Только рубли, как в дизайне.
- **Материализация производных данных в БД.** Понадобится, если встреч станут тысячи.

## Порядок реализации

1. Установить Node.js LTS; `npm install` во `frontend`, проверить `npm run build`.
2. Neon: проект, три бранча, `DATABASE_URL` в `backend/.env`.
3. Домен в Rust через TDD: доли → балансы → план → статус.
4. Схема и миграции, слой доступа к данным.
5. Ручки API поверх домена, интеграционные тесты.
6. Фронтенд: токены и шрифты → каркас и роутинг → список встреч → страница встречи → модалки.
7. Обложки: загрузка, сжатие на клиенте, раздача с кэшем.
8. PWA: манифест, иконки, офлайн.
9. Деплой: `render.yaml`, два workflow, сужение CORS, сверка со скриншотами.
