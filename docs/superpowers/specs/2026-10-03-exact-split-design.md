# Точные суммы и «платит за» — дизайн

Дата: 2026-10-03

Дополняет `2026-08-04-reckoner-design.md`. Оттуда этой спекой **заменяются** разделы «Доли» и
«Расчёт долей», колонка `entry_shares.weight_quarters` в «Модели данных» и поле `weightQuarters` в
API: четвертей больше нет. Всё остальное в исходной спеке остаётся в силе.

## Зачем

Сценарий с реальной встречи. Счёт в ресторане — 11 996 ₽, заплатил за всё Женя. По позициям
вышло так:

| Кто | Сумма |
| --- | --- |
| Аня и Женя | 3 430 |
| Настя и Алексей | 3 440 |
| Вероника | 2 906 |
| Катя | 2 214 |

Женя платит за Аню, Алексей — за Настю. Все должны скинуться Жене, кроме Ани.

Сейчас приложение это выразить не может:

1. **Точные суммы.** Расход делится только долями `1, ¾, ½, ¼, 0`. Вписать «Кате 2 214» нельзя,
   а подбирать четверти под чек бессмысленно — ими никто не пользуется.
2. **«Платит за».** Нельзя сказать, что долги Ани закрывает Женя. Сейчас это делается переводами
   вручную либо никак.
3. **Позиции чека.** У каждого в ресторане по несколько блюд, и складывать их приходится в уме,
   прежде чем вписать в поле.

Обратите внимание на сам чек: `3 430 + 3 440 + 2 906 + 2 214 = 11 990`, а не 11 996. Шесть рублей
где-то потерялись — чаевые, округление или опечатка. Такое расхождение при вводе по чеку будет
всегда, и форма обязана с ним справляться, а не упираться.

## Что решили

| Вопрос | Решение |
| --- | --- |
| Где задаётся «Женя платит за Аню» | На всю встречу, в карточке участника |
| Что с четвертями | Убираем. В строке «Делим на» вместо чипа доли — поле суммы |
| Пустое поле | «Поровну»: человек делит остаток с другими пустыми |
| Суммы вписаны у всех, но не сходятся с итогом | Разница раскладывается пропорционально вписанным суммам, до 25% |
| Как показывать пару в «Делим на» | Каждый своей строкой, у оплачиваемого подпись «платит Женя» |
| Несколько позиций на человека | Сложение прямо в поле: `390 + 1200 + 624` |
| «+ Ещё платил кто-то» | Убираем. У расхода всегда один плательщик |

Последнее — не упрощение ради упрощения. Траты в заведении всегда лежат на ком-то одном. Кроме
того, несколько записей с одной разбивкой несовместимы с точными суммами: каждая запись получала
бы «Кате 2 214», хотя сама тянет на половину счёта.

## Разбивка расхода

### Три состояния участника

| Состояние | В форме | В базе (`entry_shares`) |
| --- | --- | --- |
| поровну | пустое поле | строки нет |
| сумма N | вписано число или выражение | `rubles = N`, `N > 0` |
| исключён | строка выключена | `rubles = 0` |

Отсутствие строки означает «поровну» — как раньше отсутствие строки означало полную долю. Значит,
участник, добавленный во встречу позже, как и сейчас попадает во все старые расходы на правах
«поровну».

### Правила

`A` — сумма расхода, `F` — сумма вписанных `rubles` по участникам встречи, `E` — участники без
строки («поровну»).

1. **`E` не пусто и `F ≤ A`.** Вписанные получают ровно своё. Остаток `A − F` делится поровну между
   `E`. При `F = A` у пустых выходит 0.
2. **`E` пусто, либо `F > A`, и при этом `F > 0`.** `A` делится пропорционально вписанным суммам.
   Если `F = A`, каждый получает ровно вписанное: `A × rᵢ / F` делится нацело. Если `E` не пусто,
   пустые получают 0.
3. **`F = 0` и `E` пусто** — исключены все. Делим на всех поровну, как и сейчас.

Все три правила — одна и та же целочисленная раздача из `shares.rs`: целая часть каждому, остаток
рублей по одному тем, у кого больше дробная часть, при равенстве — по `position`, затем по `id`.
Меняются только веса: единицы для «поровну», вписанные суммы для пропорции. Участник с нулевым
весом не получает ни рубля остатка, это свойство алгоритма уже доказано тестами. Инвариант
`Σ долей == A` сохраняется во всех трёх правилах.

Домен тотален: правило 2 при `F > A` и непустом `E` срабатывает и на данных, которые API принять
не дал бы. Такие данные возникают сами: в расход с правилом 2 и скидкой (`F > A`) добавили
участника, и у него нет строки. Домен не падает и не уводит баланс от нуля — он просто считает.

### Что проверяет API при записи

- `rubles ≥ 0` и участник принадлежит встрече.
- Если после записи `E` не пусто: `F ≤ A`. Иначе 422 «вписано больше, чем потрачено».
- Если `E` пусто и `F > 0`: `4 × |A − F| ≤ A`, то есть расхождение не больше 25% от суммы
  расхода. Иначе 422. Порог отсекает опечатки вроде 22 140 вместо 2 214 и пропускает чаевые,
  сервисный сбор и обычные скидки.

Удаление участника или добавление нового может потом вывести расход за эти пределы. Это
нормально: проверки относятся к вводу, а домен считает любые данные.

## «Платит за»

У участника встречи может быть плательщик — другой участник той же встречи
(`participants.paid_by`).

- Один человек может платить за нескольких.
- Цепочек нет: у того, кто платит за других, самого плательщика быть не может, и наоборот.
- Удалили плательщика — оплачиваемый снова платит сам за себя (`on delete set null`), и его баланс
  возвращается.

### Расчёт

1. Балансы `net` считаются по каждому человеку, как сейчас.
2. Свёртка: для каждого оплачиваемого `c` с плательщиком `s` — `net[s] += net[c]`, `net[c] = 0`.
3. План переводов и статус встречи строятся по свёрнутым балансам. Оплачиваемый в плане не
   появляется никогда.

Свёртка сохраняет `Σ net == 0`: она только переносит рубли между участниками.

Домен устойчив к плохим данным. Связь игнорируется, если плательщика нет среди участников встречи
или у него самого есть плательщик. Так цепочка, возникшая, например, из двух одновременных правок,
не зациклит расчёт и не нарушит инвариант.

«Внёс N ₽» в карточке остаётся личным: это сумма расходов, которые человек оплатил сам.

Свёртка живёт в новом модуле `backend/src/domain/wallets.rs`. «Кошелёк» — это человек, за которого
никто не платит, вместе с теми, за кого платит он.

## Пример: ресторан

Женя платит 11 996. Настя → платит Алексей, Аня → платит Женя. Вписано: Катя 2 214,
Алексей 3 440, Женя 3 430, Вероника 2 906. Настя и Аня выключены. `F = 11 990`, пустых полей
нет — работает правило 2.

| | вписано | доля | остаток `11 996 × rᵢ mod 11 990` |
| --- | --- | --- | --- |
| Катя | 2 214 | 2 215 | 1 294 |
| Алексей | 3 440 | 3 441 + 1 = **3 442** | 8 650 |
| Женя | 3 430 | 3 431 + 1 = **3 432** | 8 590 |
| Вероника | 2 906 | 2 907 | 5 446 |
| **Итого** | 11 990 | **11 996** | |

Целые части дают 11 994. Два оставшихся рубля уходят двум наибольшим остаткам — Алексею и Жене.

Балансы после свёртки: Женя `+8 564`, Катя `−2 215`, Алексей `−3 442`, Вероника `−2 907`,
Аня и Настя `0`. План — три перевода Жене: 2 215, 3 442, 2 907.

Вариации, которые должны давать то же самое или предсказуемо иное:

- Вписать Алексею и Насте по 1 720 вместо 3 440 Алексею: доли 1 721 + 1 721 = 3 442. План тот же.
- Оставить поле Кати пустым: работает правило 1. `F = 9 776`, Кате достаётся весь остаток — 2 220.
  Остальные платят ровно вписанное.

Эти числа — готовые тестовые векторы для домена и для превью на фронте.

## Модель данных

Миграция `backend/migrations/0002_exact_shares_and_paid_by.sql`. Применяется при старте бэкенда,
как и `0001`.

```sql
entry_shares
  entry_id        uuid    not null references entries(id)      on delete cascade
  participant_id  uuid    not null references participants(id) on delete cascade
  rubles          bigint  not null check (rubles >= 0)          -- было weight_quarters
  primary key (entry_id, participant_id)

participants
  + paid_by  uuid  references participants(id) on delete set null
  + check (paid_by <> id)
```

Принадлежность `paid_by` той же встрече и отсутствие цепочек проверяет API. Так же сейчас
проверяется принадлежность `payer_id` и `recipient_id`.

### Старые четверти

- Вес `0` переводится в `rubles = 0`. Это точный эквивалент: исключён.
- Неполные веса `1..3` в новую модель напрямую не ложатся. Скорее всего, в проде их нет.

**Перед деплоем** выполнить в Neon SQL Editor на бранче `production`:

```sql
select count(*) from entry_shares where weight_quarters between 1 and 3;
```

- **0** (ожидаемо): миграция переводит `0 → 0` и удаляет колонку. В начале миграции стоит защита:
  если неполные веса всё же есть, она падает через `raise exception` с понятным текстом. Сервер
  при этом не поднимается, Render оставляет работать старую версию, и деньги не меняются молча.
- **больше 0**: дописываем честную конвертацию. Неполная доля превращается в `rubles` — ровно ту
  сумму, которую человек платит сейчас, а полные доли остаются без строки. Доли всех участников
  при этом сохраняются до рубля. Полные доли у всех одинаковы по весу, поэтому лишние рубли между
  ними и до, и после раздаются по `position`.

## API

Каждая мутация по-прежнему возвращает встречу целиком.

| Где | Было | Стало |
| --- | --- | --- |
| `participants[]` в ответе | — | `paidById: string \| null` |
| `participants[].netRubles` | личный баланс | баланс после свёртки: у плательщика вместе с оплачиваемыми, у оплачиваемого 0 |
| `POST /participants`, `PATCH /participants/:pid` | — | принимают `paidById`; `null` — платит за себя |
| `entries[].shares[]` и тело записи | `{ participantId, weightQuarters }` | `{ participantId, rubles }` |
| `entries[].sharedByAll` | — | без изменений: `true`, когда строк разбивки нет |

Новые 422:

| Поле | Когда |
| --- | --- |
| `paidById` | участник из другой встречи; сам себе; у выбранного плательщика есть свой плательщик; у этого участника уже есть оплачиваемые |
| `shares` | `rubles < 0`; `F > A` при пустых; расхождение больше 25% без пустых |

`shares` у перевода по-прежнему запрещены. Переводы с участием оплачиваемого не запрещаются: они
сворачиваются в кошелёк так же, как расходы.

### Лог

Тексты без рода, как и все остальные:

| Событие | Текст |
| --- | --- |
| Назначили плательщика | `Аня: теперь платит Женя` |
| Сняли плательщика | `Аня: снова платит за себя` |

Если в том же запросе поменялись имя или аватар, к этим строкам добавляется прежняя
`Профиль участника обновлён: …`. Если участника добавили сразу с плательщиком, после
`Аня присоединяется к встрече` пишется `Аня: теперь платит Женя`.

### Порядок деплоя

Сначала бэкенд, потом Pages. Пока Pages не обновился, старый фронт может добавлять только расходы
«поровну на всех» (`shares: []`). Расход с исключённым человеком получит 422 и не сохранится —
ничего не испортится. Окно в несколько минут, отдельной совместимости не делаем.

## Интерфейс

### Модалка расхода

```
Новый расход                                    ✕
Кто заплатил
[ 🐨 Женя                ▾ ] [   11 996 ₽ ]

На что
[ Ресторан                                    ]

Делим на                     пустое поле — поровну
┌─────────────────────────────────────────────┐
│ 🦊 Катя            [ 390 + 1200 + 624 ] [+] │
│                         = 2 214 → 2 215 ₽   │
│ 🐝 Алексей                 [   3 440 ₽ ]    │
│                                 → 3 442 ₽   │
│ 🦉 Настя  (приглушено)               —      │
│    платит Алексей                           │
│ 🧞 Аня    (приглушено)               —      │
│    платит Женя                              │
│ 🐨 Женя                    [   3 430 ₽ ]    │
│                                 → 3 432 ₽   │
│ 🦔 Вероника                [   2 906 ₽ ]    │
│                                 → 2 907 ₽   │
└─────────────────────────────────────────────┘
+6 ₽ разложены пропорционально
                              [Отмена] [Добавить]
```

- **Плательщик один.** Блок «+ Ещё платил кто-то», последовательная отправка нескольких записей и
  сообщение «часть расходов могла сохраниться» удаляются.
- **Тап по аватару и имени** включает и выключает человека. Это кнопка с хит-таргетом ≥ 40 px.
  Выключенная строка приглушена, вместо поля стоит «—».
- **Поле суммы:**
  - пустое — серым плейсхолдером видна доля «поровну», посчитанная превью;
  - введено выражение из нескольких слагаемых — под полем `= 2 214`;
  - правило 2 сдвинуло долю — под полем итог `→ 2 215`; если выражения нет, только `→ 2 215`.
- **Кнопка «+»** появляется рядом с полем в фокусе: на цифровой клавиатуре телефона плюса нет.
  Нажатие дописывает `+` в конец и не уводит фокус. На компьютере плюс можно просто напечатать.
- **Строка состояния** под списком, одна из:
  - `Остаток 4 200 ₽ — поровну на 3` — правило 1, когда вписаны не все. Если не вписан никто, это
    обычное деление поровну, и строки нет;
  - `+6 ₽ разложены пропорционально` / `−300 ₽ вычтены пропорционально` — правило 2 с расхождением;
  - красная ошибка, «Добавить» неактивна: `Вписано 12 500 ₽ — больше, чем потрачено` /
    `Вписано 31 916 ₽ из 11 996 ₽ — проверьте суммы`.
- **Подпись у оплачиваемого:** `платит Женя` под именем.
- **Правка расхода** восстанавливает строки: нет строки — пустое поле, `0` — выключен, `N` — `N`.
  Выражения не хранятся, в поле приходит итог. Забытое блюдо дописывается к нему: `2214 + 350`.

### Выражения в поле суммы

Тот же разборщик работает и в поле суммы плательщика.

- Слагаемые разделяются `+`, пробелы внутри и вокруг игнорируются, десятичный разделитель — `,`
  или `.`.
- Каждое слагаемое переводится в копейки, сумма округляется вниз до рубля **один раз** — для итога.
  Подпись «Копейки не учитываем — суммы округлены вниз» показывается, если итог был дробным.
- Пустые слагаемые (`390 +`, висящий плюс во время набора) пропускаются.
- Любое нечисловое слагаемое делает поле невалидным: рамка красная, «Добавить» неактивна.
- Минуса нет: скидка на отдельного человека в этот объём не входит.

Код — в `frontend/src/domain/amountExpression.ts`. `parseAmount` из `format.ts` становится частным
случаем: одно слагаемое.

### Превью долей

`frontend/src/domain/sharePreview.ts` переписывается под три правила. Дублирование доменного
алгоритма остаётся осознанным, как и раньше: доли показываются на каждый ввод, а записи ещё нет.
Расхождение ловят тесты на общих векторах.

### Модалка участника

Новое поле «Кто платит» (`Select`):

- первый вариант — `Платит за себя`;
- дальше участники встречи, кроме самого человека и тех, у кого уже есть плательщик;
- если человек сам платит за других, поле неактивно и под ним подсказка
  `Уже платит за других: Аня, Настя`.

Поле есть и при добавлении, и при правке.

### Карточка участника

- У оплачиваемого вместо баланса серым `платит Женя`. «Внёс N ₽» остаётся.
- У плательщика баланс общий. Рядом с именем приглушённо `+ Аня` (через запятую, если оплачиваемых
  несколько).

### Долги

- Список переводов не меняется: оплачиваемые в нём и так не появятся.
- Матрица и полосы баланса показывают только кошельки — тех, за кого никто не платит. Подпись
  кошелька: `Женя + Аня`.

### История

Сейчас у расхода с неполными долями подпись `· делят не все`. Теперь:

- есть хотя бы одна строка с `rubles > 0` — `· точные суммы`;
- есть только строки с `0` — `· делят не все`;
- строк нет — без подписи.

## Тесты

**Домен** — через TDD, без базы:

- правило 1: остаток поровну, `F = A` даёт пустым 0, раздача остатка по `position`;
- правило 2: `F = A` даёт ровно вписанное; расхождение вверх и вниз; нулевой вес не получает рубля
  остатка; `F > A` при непустом `E` — пустым 0;
- правило 3: исключены все;
- ресторан из раздела «Пример» со всеми вариациями — ровно с теми числами;
- свёртка: один плательщик за нескольких, удалённый плательщик, игнорирование цепочки и ссылки на
  чужого;
- property-тест (`proptest`) расширяется на случайные смеси «поровну / сумма / исключён» и
  случайные `paid_by`, включая цепочки. Инварианты: `Σ долей == A` для каждого расхода,
  `Σ net == 0`, у оплачиваемого `net == 0`, план закрывает встречу в ноль.

**API** — интеграционные тесты на тестовом бранче Neon:

- все новые 422 из таблицы выше, включая цепочку в обе стороны;
- `rubles` пишутся и читаются без изменений, отсутствие строки остаётся отсутствием;
- `netRubles` приходит свёрнутым, а план не содержит оплачиваемых;
- удаление плательщика обнуляет `paidById` у оплачиваемых;
- строки лога о назначении и снятии плательщика.

**Фронт** — Vitest:

- `sharePreview` на тех же векторах, что и Rust, включая ресторан;
- `amountExpression`: `390 + 1200 + 624` → 2 214; `1 250,50 + 99,50` → 1 350; `390 +` → 390;
  `0,1 + 0,2` без потерь на плавающей точке; мусор → невалидно; пустая строка → пусто, не ноль.

**Вручную в браузере** — собрать ресторан целиком на локальном сервере и сверить долги с таблицей
из раздела «Пример».

## Рассмотрено и отклонено

| Вариант | Почему нет |
| --- | --- |
| «Платит за» в каждом расходе отдельно | Для пар это задаётся один раз на встречу. Разовый случай выражается точными суммами |
| «Платит за» и на встречу, и в расходе | Самый сложный вариант и в модели, и в интерфейсе, а выигрыш не нужен |
| Переключатель «Поровну / Точно» | Смешанный случай «Кате 2 214, остальные поровну» не выразить |
| Оставить четверти рядом с суммами | Строка перегружена, а четвертями не пользуются |
| Не сохранять, пока суммы не сойдутся | За столом приходится решать, кто доплачивает 6 ₽ |
| Разницу — поровну на всех | Нечестно для чаевых: заказавший меньше платит столько же |
| Пара одной строкой «Женя + Аня» | Сложнее логика деления поровну, а пары без «платит за» всё равно делятся руками |
| Список позиций под строкой | На 6 человек по 3–4 блюда модалка превращается в длинную ленту |
| Хранить выражение, а не итог | Дописать забытое к итогу так же просто: `2214 + 350` |
| Одна запись с несколькими плательщиками | Траты лежат на ком-то одном; убрали саму возможность нескольких плательщиков |

## Вне объёма

- Скидка или наценка на отдельного человека (минус в выражении).
- Распознавание чека по фото.
- Перенос «платит за» между встречами: у каждой встречи свой состав и свои связи.
